### Package layout
- `dev.simplified.resourcepath` â€” ResourcePath inspection + visitor + evaluator + change listener + startup activity.
- `dev.simplified.contract` â€” **annotation-neutral** contract-DSL grammar infrastructure: `ContractAst`, `ContractLexer`, `ContractParser`, `ContractParseException`. Reusable for any annotation that carries the same contract DSL.
- `dev.simplified.xcontract` â€” **specific to the `@XContract` annotation**: `XContractInspection` (declaration-side), `XContractCallInspection` (caller-side), `XContractInferredAnnotationProvider` (bridge to JetBrains `@Contract`), `XContractTranslator` (AST â†’ `@Contract` string).
- `dev.simplified.classbuilder.apt` â€” JSR 269 annotation processor: `ClassBuilderProcessor` (entry, registered via `META-INF/services/javax.annotation.processing.Processor`, dispatches class/record targets to the mutator and interface targets to the sibling emitter), `FieldSpec` (per-field IR), `SourceIntrospector` (Trees-API bridge for reading declared initialisers), `AnnotationLookup` (mirror attribute reader), `BuilderConfig` (resolved annotation attributes), `NamePattern` + `SetterScheme` + `BuilderScheme` (the naming trio, below), `BuilderEmitter` (legacy source generator; now only handles interface targets since classes/records use AST mutation), `InterfaceImplEmitter` (emits the `<Name>Impl` concrete class for interface targets, copying each accessor's `@BuildFlag` onto the field it synthesises - re-escaping string attributes, since a `pattern` regex routinely carries backslashes), `ImportRegistry` (the single import bookkeeper both emitters delegate to).
  - **`ImportRegistry` keys on the simple NAME, not the FQN, and that inversion is the whole point.** Both emitters previously kept their own import set keyed on the fully-qualified name while returning the simple one, so two types sharing a simple name each got a single-type import and the generated file failed to compile with `reference to Arrays is ambiguous` - on a line the consumer cannot edit. First claimant wins and gets the import; every later type wanting that name is spelled out inline. Three claims are easy to miss and all three are load-bearing: a `java.lang` type must claim even though it takes no import entry, or a field typed `acme.String` imports itself and silently reassigns every other `String` in the file; a same-package type likewise; and `declare(simpleName)` claims the names the emitter writes **bare** - the target, the `Impl`, the `Builder`, `@Override` - which nothing routed through the import path at all. Claims are made before the first `use()` can spend one, since a claim registered late loses the race silently.
  - **The naming trio is the single place any generated name is minted.** `NamePattern` holds the `{}` expander and the validator (`patternError(pattern, placeholderRequired)` - that boolean *is* the per-field / once-per-target distinction). `SetterScheme` resolves the six per-field patterns and mints their names; `BuilderScheme` resolves the five once-per-target names, already expanded and already emptied where suppressed. All three are deliberately free of javac, PSI, and `FieldSpec` references so `:plugin` shares the instances, and the five naming sites (`FieldMutators`, `SelfTypedSetters`, `BootstrapMethodFactory`'s seed-setter lookup, `BuilderEmitter`, and the editor's `GeneratedMemberFactory`) all route through them. Each used to carry a private `methodName(String, boolean forceBoolean)` plus inline `"is"` / `"add"` / `"put"` / `"clear"` literals that had to agree byte-for-byte or the editor's autocompletion diverged from javac's output.
  - `BuilderConfig` keeps flat `builderName()` / `builderMethodName()` / â€¦ accessors delegating to its `BuilderScheme`, so the ~30 emitter call sites did not move when the annotation surface regrouped.
- `dev.simplified.args.{apt,mutate}` â€” the constructor family. `ArgsMode` (the four settings), `ArgsField` (per-field IR), `ArgsSelection` (the rule), `ArgsFieldSelector` (tree walk), `ArgsConfig` (resolved annotations plus the `@ClassBuilder` inference), `ArgsConstructorFactory` (the shared mint), `ArgsConstructorMutator` (the orchestrator). Dispatched from `ClassBuilderProcessor` rather than a processor of its own, for the same reason `@Getter` is: **ordering has to be a guarantee**, and the constructor pass must run before `@Lazy` retypes its parameters and before the builder pass decides whether to synthesise its own.
  - **`ArgsField` is deliberately not `FieldSpec`.** `FieldSpec.sourceInitializer` is populated only when the builder wants the initializer as a default, so it cannot answer "is this final field already assigned" in general; `JCVariableDecl.init != null` always can.
  - **`ArgsSelection` is javac-free, model-free and PSI-free**, holding the selection rule as a function of six booleans. The processor extracts those facts from a `JCVariableDecl` and the IDE from a `PsiField` - the facts cannot be shared, but the decision must be, or the signature in the gutter contradicts the one javac emits. Same mitigation the naming trio uses.
  - **`ArgsConstructorFactory` is the single place a constructor declaration is minted**, including the builder's. `AllArgsConstructorFactory` keeps only the parameter *shaping* the builder alone needs - the `Supplier<T>` retype for an instance default and the container-plus-marker pair for a collected one - and delegates the `names.init` `MethodDef`, the access flags and the coverage marker here.
- `dev.simplified.classbuilder.mutate` â€” javac AST mutation pipeline: `JavacBridge` (reflective gateway to `JavacProcessingEnvironment` internals), `MutationContext`, `BuilderMutator` (concrete/record orchestrator), `SuperBuilderMutator` (abstract-target and concrete-subclass orchestrator with self-typed generics), `AnnotatedSuper` (the annotated direct super plus the type arguments the target passes it), `NestedBuilderFactory`, `BootstrapMethodFactory`, `CopyConstructorFactory`, `AllArgsConstructorFactory` (synthesises the all-args ctor `build()` calls, on plain classes that declare none), `FieldMutators`, `SelfTypedSetters`, `JavacTypeFactory`, `AstMarkers`.
  - **`from(T)` / `mutate()` seeding is a ladder, not a bean-accessor assumption.** `BootstrapMethodFactory.readFrom` resolves each field in order: `@ObtainVia`, then a record component's canonical accessor, then a `@Lazy` field's synthesised getter (pinned, since storage is `Lazy<T>` and a field read would yield the wrapper), then an author-declared zero-arg accessor in any spelling a getter generator produces (`getX` / `isX` / bare `x`), then a direct field read, then the bean call with a `NOTE`. A declared accessor deliberately outranks the field read: when the author wrote the accessor, a normalising or defensive-copying body is the behaviour they asked for. The direct read is legal for anything the target declares - `from(T)` and `mutate()` are members of the target - and for an inherited field only when `public`/`protected`/same-package. This is what closed F1: before it, the emitted `instance.getX()` named a method nobody had written, so a `@ClassBuilder` target had to carry Lombok `@Getter` whether or not it wanted public accessors. The last rung stays a `NOTE` rather than an error because an accessor generated later in the same round is invisible to any scan of the model, so erroring would regress a build that works.
  - `MutationContext.declaresAccessor(name)` backs rung four. The snapshot is taken **in the constructor, before any mutator appends** - the only moment "declared by the author" and "present on the tree" are the same set, since `LazyFieldMutator` synthesises a getter onto the target immediately afterwards. It unions the target's own `defs` with `Elements.getAllMembers` (which is the only view of an inherited accessor, and matters for a SuperBuilder subclass seeding its parent's fields), minus `java.lang.Object`'s own methods.
  - **Generic targets**: a nested `Builder` is `static` and cannot see the enclosing type's variables, so `MutationContext.typeParams()` / `typeArgs()` / `targetType()` / `builderType()` mint fresh declaration and reference nodes (javac trees cannot be shared between parents, so every call returns new ones). Every emitter goes through those rather than `make.Ident(builderName)` â€” returning the bare name from a setter erases the builder to a raw type and silently drops the parameter for the rest of the chain. Static members (`builder()`, `from(T)`, non-instance `$default$` providers) declare their own copies. `MutationContext.selfTypeName()` / `selfBuilderName()` pick the SuperBuilder `T` / `B` names, dodging a collision when the target declares parameters by those names; both `SuperBuilderMutator` (which declares them) and `SelfTypedSetters` (which returns them) read from there so they cannot drift. `compat/` subpackage carries `JavacCompat` interface + `JavacCompatFactory` (single entry point, ready to version-gate) + `v17/JavacCompatV17` baseline. Every supported JDK (17 through 25) uses the baseline today; a future divergence is absorbed by adding a new `v<N>/JavacCompatV<N>` subclass plus one gate in the factory.
- `dev.simplified.classbuilder.editor` â€” IntelliJ editor-side synthesis: `ClassBuilderAugmentProvider` (surfaces bootstrap methods to the PSI layer so autocompletion works before the first javac round), `ClassBuilderLineMarkerProvider` (gutter icon on `@ClassBuilder` annotations), `GeneratedMemberFactory` + `GeneratedMemberMarker` (synthesis helpers and provenance key), `PsiFieldShape` + `PsiFieldShapeExtractor` (PSI analogue of `FieldSpec`), `OptionalSetterNullIntention` (Alt+Enter fix for the Optional dual setter's one ambiguous call).
  - **`OptionalSetterNullIntention`** rewrites a bare `x(null)` to `x(Optional.empty())`. An `Optional<T>` field generates `x(T)` + `x(Optional<T>)` deliberately - the wrapping belongs inside the builder, not at every call site - and the price is that a *literal* null is ambiguous per JLS 15.12.2.5. Only `Optional.empty()` is offered: the raw overload wraps with `ofNullable`, so `x((T) null)` stores the identical value while saying less. Keyed on the **candidate shape** (one `Optional<T>` param, one `T` param, same name) rather than on `GeneratedMemberMarker`, because a builder read from a compiled dependency carries no marker and the fix is equally right there. See notes C8 for why the single-setter mode was closed instead.
  - **Generic targets**: `GeneratedBuilderClass` re-declares the target's type parameters (bounds included) because it is `static`. Those copies are *distinct* `PsiTypeParameter`s from the target's, so anything declared inside the Builder must be expressed in them â€” `GeneratedMemberFactory.remap(...)` builds the targetâ†’Builder substitutor and `PsiFieldShapeExtractor.fromClass/fromRecord` apply it before classification, which is what makes a `Builder<String>` receiver actually substitute the setter parameter. Leaving a setter holding the target's parameter compiles fine and looks right in the PSI, but the editor then rejects every call with "cannot be applied to". Static bootstraps (`builder()`, `from(T)`) declare their own method-level copies via `DocProxyingLightMethodBuilder.withTypeParameters(...)` â€” `LightMethodBuilder` has a `getTypeParameterList()` but no setter, so the list is held in the subclass and surfaced through three overrides. `mutate()` is an instance method and uses the target's directly.
  - **SuperBuilder chains**: `ChainRole` classifies a target the same way `BuilderMutator.mutate` branches (abstract? annotated direct super?) so the editor's model matches what javac emits. An `ABSTRACT_ROOT`/`CHAINED_ABSTRACT` Builder is `abstract` and self-typed `<T extends Target, B extends Builder<T,B>>` with setters returning `B` and abstract `self()`/`build()`; a `CONCRETE_LINK` sets `extends Parent.Builder<superArgsâ€¦, Target, Builder>` via `GeneratedBuilderClass.setSuperType(...)`. Two things are load-bearing and easy to get wrong: (1) without the `extends`, the platform's inherited-member lookup has nothing to walk and every setter declared further up reads as unresolved; (2) without the self-typed `B`, an inherited setter returns the *parent's* Builder, so `.parentSetter(...).childSetter(...)` resolves in one call order and not the other. The parent's synth Builder is resolved through the augment-aware `getInnerClasses()` rather than by name, so the reference points at the same instance the platform hands out; re-entering for the parent is safe because `IN_PROGRESS` is keyed per target and a root has no super to walk to. Inherited setters are *not* copied onto the link â€” they arrive through the supertype, which is why `findMethodsByName("t", false)` is empty there while `(â€¦, true)` finds it.
- `dev.simplified.classbuilder.validate` â€” runtime: `BuildFlagValidator` (reflective, per-class cached), `BuilderValidationException`, `Strings.formatNullable` helper.
- `dev.simplified.args.{editor,inspect}` â€” `ArgsAugmentProvider` (a fifth `lang.psiAugmentProvider`), `ArgsInference`, `ArgsInferredAnnotationProvider` (a third `lang.inferredAnnotationProvider`), `ArgsConstructorInspection`, `ArgsConstants`.
  - **The augment provider is mandatory in both directions**, which is unusual. Without it a `@AllArgsConstructor` target's every call site is unresolved and the IDE never runs javac, so "until the next build" is no mitigation - but a `@NoArgsConstructor(access = PRIVATE)` also exists to **remove** the public default the platform assumes, and contributing a private one is what makes an outside `new Target()` report the error javac will give.
  - **The inferred annotation is never written into the author's source.** That would be a document write on every reanalysis: it churns VCS diffs, fights undo, and would have to be un-written the moment a `@BuilderIgnore` lands. It is surfaced twice instead - as an `InferredAnnotationProvider` (so Ctrl+Q renders it) and in the `ClassBuilderLineMarkerProvider` tooltip, which carries the **resolved signature** as well as the name, because adding one `@BuilderIgnore` silently shortens the constructor and breaks every hand-written `new Target(...)` in the package.
  - **The inference is set equality**, not "nothing was excluded". The two lists diverge in both directions, and a value class whose every field is an initialized `final` infers `@BuilderArgsConstructor` with nothing excluded - the common case, not the exception.
  - **`ArgsConstants` matches field annotations on their simple name rather than resolving them.** Not an optimisation: resolving a field annotation re-enters every augment provider registered for the class, the builder's included, which reads the same annotation on the way through - and the platform answers that cycle by disabling caching and logging an error. The gate itself is not duplicated; `ClassBuilderAugmentProvider.synthesisesConstructor` is the one public reading of it.
- `dev.simplified.classbuilder.inspect` â€” IDE-side: `ClassBuilderFieldInspection` (flags misuse of companion annotations at source-edit time, plus malformed `@SetterNames`/`@BuilderNames` patterns and the four members that refuse `NONE`), `GetterVisibilityInspection` (below), `ClassBuilderConstants` (shared FQNs + attribute readers, including `namingStyle`/`setterScheme`/`builderScheme` and the `writtenStringAttr` reader that mirrors the processor's `getElementValues()` written-vs-defaulted view â€” `stringAttr` uses `findAttributeValue` and folds empty into the fallback, so it cannot tell an explicit value from an unwritten attribute). The bootstrap-methods inspection was retired in 1.3.0 since the methods are now auto-injected.
- `dev.simplified.accessor.inspect` â€” `AccessorInspection` + `AccessorConstants`. The inspection is **pure error-mirroring**: every check restates a diagnostic `AccessorMutator` already emits (`@Setter` on a `final` field, `@Setter` with `@Lazy`, a redundant `@Getter` on a `@Lazy` field, `@Getter`/`@Setter` on a record or interface), so its value is timing and position rather than the message. **What it is load-bearing for is the type-level/field-level asymmetry**, which it has to copy exactly: `AccessorMutator.accepts` is silent when a rejection arises from a type-level fan-out and only reports when the author singled the field out, because annotating a class is a blanket request rather than a claim about any one field. Reproduce it approximately and a bare `@Getter` on a class holding one `final` field lights up wrongly. It also validates the per-field `name` pattern through `NamePattern.patternError(pattern, true)` - placeholder mandatory - mirroring `ClassBuilderProcessor.validateAccessorName`. `AccessorScheme.resolve` passes a written name straight to `NamePattern.inherit`, so without the check a pattern missing its `{}` gives every field the same accessor name and `name = "-"` mints a method named `-`. **The sentinel is rejected rather than honoured**: these annotations suppress through `AccessLevel.NONE`, so nothing on the accessor path reads `"-"` as an opt-out and it would reach javac as a method name. The check runs on a type-level annotation as well as a field-level one, and matters more on the type - there a missing placeholder collides every field on the class, where on a field it only collides with whatever else claims that name.
- `dev.simplified.log.{apt,mutate}` and `dev.simplified.log.{editor,inspect}` â€” `LogProcessor` (a sixth entry in the services file) and `LogFieldMutator`, against `LogAugmentProvider` (an eighth `lang.psiAugmentProvider`) and `LogInspection` + `LogConstants` (a seventeenth `localInspection`). The whole feature is one field, so there is no line marker and no icon: the augment provider exists because without it every `log.*` call reads red on source that builds, and the inspection says up front what the processor errors on - an illegal target kind, a `name` failing `NamePattern.patternError`, and the `NONE` sentinel, which is an error here rather than a suppression because the field is the annotation's only output.
- `dev.simplified.silentthrows.{apt,mutate}` and `dev.simplified.cleanup.{apt,mutate}` â€” the two body rewrites, and the first passes in the project that change control flow rather than appending a member. **The rewrite ordering contract is the part to know:**
  - **Both must run after `LazyFieldMutator`, and this binds `@Cleanup` exactly as hard as `@SilentThrows`.** `rewriteConstructorParams` reads `method.body` and hands it to `rewriteAssignmentsInBlock`, which iterates `block.stats` **flat, with no recursion**, matching only a top-level `this.<f> = <f>`. Either rewrite moves statements one level down - `@SilentThrows` relocates the whole list into a `JCTry`, `@Cleanup` relocates the tail after the declaration - so the `Lazy.of(...)` wrap is skipped and javac reports `Supplier<T>` against `Lazy<T>` on a constructor line the author never wrote. Pinned by `PassOrderingTest`, verified negatively: the passes were temporarily moved to the front of the pipeline and the tests failed with exactly that diagnostic.
  - **Order between the two rewrites is free.** `@Cleanup` mutates the enclosing `JCBlock.stats` in place so its identity survives re-parenting, and `@SilentThrows` re-parents that same instance under a new block, so a recursive scan still reaches the declaration. Both interleavings produce the identical tree and a close failure lands inside the outer `catch (Throwable)` either way. The rewrites run last, after every member injection.
  - **A shared idempotency marker is not composable.** Both passes originally guarded on `AstMarkers.markGenerated`, and the single global set made them mutually exclusive - whichever ran first silenced the other, and `@SilentThrows` then emitted nothing at all whenever `@Cleanup`'s `"*"` processor was registered, which is every consumer build. The annotation compiled away to nothing and the only symptom was a compile error on the author's own line. `AstMarkers` gained `markPass(node, pass)` / `isPassMarked(node, pass)`, a per-pass namespace; `GENERATED` keeps its authorship meaning.
  - `shared/javac/AnnotationSpelling` is the one place deciding whether a written annotation name refers to a given FQN, since a single-type import settles it in both directions. Without it a foreign `@Lazy` defeated the deferral and a foreign `@Cleanup` was rewritten.
- `dev.simplified.silentthrows.{editor,inspect}` and `dev.simplified.cleanup.inspect` â€” the editor half, and the only feature here whose editor story is *subtractive*. `SilentThrowsExceptionHandler` (`com.intellij.custom.exception.handler`) tells the platform to stop reporting an unhandled checked exception the mutation absorbs; without it 26 files sit red on every keystroke while the build succeeds.
  - **The walk stops at the first lambda, method reference or class boundary and returns false.** Each is its own exception-analysis context that the wrap does not reach into, so walking through one would turn the editor **green on code javac rejects** - strictly worse than the red editor the handler exists to fix. The workspace already depends on the boundary being real: a facade method puts a call to another annotated method inside `CompletableFuture.supplyAsync(() -> â€¦)`, and it compiles only because the *inner* method is itself annotated.
  - `CleanupSuppressor` (`lang.inspectionSuppressor`) silences the resource-leak inspections on a variable the mutation closes. **`isSuppressedFor` matches the `suppressId`, not the `shortName`** - `InspectionProfileEntry.getSuppressId` resolves through `LocalInspectionEP.id`, mapped from the XML `suppressId` attribute - so matching `AutoCloseableResource` / `IOResource` would silently never fire. It matches `resource` and `IOResourceOpenedButNotSafelyClosed`, and gates on the `@Cleanup` element *before* looking at the tool id, since `resource` is a deliberately generic id shared with the `// noinspection resource` form.
- `dev.simplified.utility.editor` â€” `UtilityClassAugmentProvider`, a sixth `lang.psiAugmentProvider` and **the only one that overrides `transformModifiers` rather than `getAugments`**. `members = MAKE_STATIC` adds `static` by mutating the javac AST, which leaves nothing in the PSI to read, so a class-qualified call to such a member read as an instance member referenced from a static context - an error on source that builds cleanly, and indistinguishable from a real one. `transformModifiers` is the one platform hook that alters an element the platform already built, and `PsiModifierListImpl.hasModifierProperty` routes through it, so the contributed modifier is seen by the very check that was complaining.
  - **It runs on the `hasModifierProperty` path for every modifier list in the project**, so every rejection ahead of the annotation read is a cheap syntactic test, the annotation is matched on its simple name rather than resolved, and nothing inside calls `hasModifierProperty` - the incoming `Set<String>` is the authority on what is already written.
  - The selection rule is `UtilityClassMutator.applyMemberPolicy`'s member for member. It reads the owner from `getParent()` rather than `getContainingClass()` **because the processor walks the target's own definitions**: a local class lives in a method body, which javac's round scan never descends into, and `getContainingClass()` would have staticised it.
- `dev.simplified.utility.inspect` â€” `UtilityClassInspection` + `UtilityClassConstants`. **This is the half that was supposed to justify the annotation's opt-in split.** The contract is "report, don't rewrite", and `REQUIRE_STATIC` was always meant to report an instance member *and* offer the fix; only the reporting shipped, as a hard `Diagnostic.Kind.ERROR` carrying the remedy as message text. So annotating an existing class gave a red build with no warning first, for a remedy that is purely mechanical - which is why the **"Make static" `LocalQuickFix` is the point of the inspection**, not a garnish. Also mirrors `constructorAccess = NONE`, an author-declared constructor defeating the annotation (a WARNING, since the annotation backs off rather than breaking), and every illegal target kind from `UtilityClassProcessor.isLegalTarget`. `MAKE_STATIC` silences the instance-member check entirely - that mode legalises exactly what the default rejects.
  - **A local class inside an inner class is deliberately silent on both sides.** javac's round scan never descends into a method body, so `@UtilityClass` there is a no-op the build accepts; walking the nesting chain out through the enclosing method would have made the IDE report an error on source that compiles. Pinned from both directions, by an `aptTest` asserting the compile succeeds and an inspection test asserting no highlight.

- `dev.simplified.shared.apt` â€” the annotation-neutral half of the whole-object features, beside the existing `AnnotationLookup` and `SourceIntrospector`. `MemberSpec` (per-member IR), `MemberPolicy`, `MemberSelector`, `MemberShape`, `SuperResolver`.
  - **`MemberPolicy.keepTransient` is the whole reason the selector takes a policy rather than hard-coding a rule.** `@EqualsAndHashCode` drops `transient` and `@ToString` keeps it, and that is the only place the two differ. A shared selector that silently applied the equality rule to both would be a correctness bug with **no compile signal** - the annotation would keep working and quietly print less than it holds - so the divergence is a parameter rather than an assumption.
  - **`MemberSpec` is deliberately not `FieldSpec`**, for the same reason `ArgsField` is not: `FieldSpec` is shaped by what a builder needs (collector kind, singular name, retained initializer), it filters `transient` out before construction, and it folds in `@ClassBuilder`'s own exclusions - which say what a *caller supplies*, not what the object *is*. `PipelineContext.activeIds` is exactly the shape that distinction protects.
  - **`MemberShape` is chosen from the read expression's type and reads array depth off the `TypeMirror`**, which makes it immune to type-use annotations without a text-stripping step: `float @NotNull []` is a one-dimensional primitive array whatever it looks like in source. A record is walked through its enclosed fields rather than `getRecordComponents()` - the two are one-to-one and in the same order, and the field is where an annotation targeting `FIELD` is reliably visible after the compiler has propagated it off the component.
- `dev.simplified.shared.javac.MemberTerms` â€” the per-member expression emitter for all three generated members. One emitter because the interesting cases are the same cases: an array read by content, a float inducing one partition in `equals` and the matching one in `hashCode`. **Getting either right in one member and wrong in another is worse than getting both wrong**, since the inconsistency has no symptom until a hash table starts losing entries. Every read arrives as a `Supplier<JCExpression>` rather than a node, because a javac tree cannot be shared between two parents and the reference and long-fold terms need the same read two or three times.
- `dev.simplified.equality.{apt,mutate}` and `dev.simplified.tostring.{apt,mutate}` â€” `EqualityConfig` / `ToStringConfig` (resolved attributes plus the `MemberPolicy` each hands the selector), `MemberWarnings`, `EqualityMutator`, `ToStringMutator`. Dispatched from `ClassBuilderProcessor` for the same reason `@Getter` and the constructor family are, and specifically **after `processAccessors`**: `useAccessors` has to see every accessor the accessor pass minted, and the collision snapshot has to be able to tell an author-written `equals` from one this pipeline produced. They stay **above** the two body rewrites, which relocate statements one level down.
  - **`MemberWarnings` reports the two limits no emission can close**, and the container-of-array check is the one that must not over-fire. `byte[]`, `int[][]` and `Vector3f[]` are all handled correctly by the flat/deep split; the unreachable case is an array *behind a type parameter* - `List<byte[]>`, `Optional<byte[]>`, `Map<K,int[]>` - where the container delegates to its element's `equals` and an array inherits `Object`'s. Warning on plain arrays would train the reader to ignore the check that matters. The bare `java.util.Collection` sibling warns for a different reason: that interface specifies no `equals` contract at all.
- `dev.simplified.accessor.apt.AccessorReads` â€” the type-checked accessor resolver `useAccessors` needs, deliberately separate from the builder's seeding ladder. It lives here rather than in `shared.apt` because it has to reach `AccessorScheme`, and the naming trio is the single place any generated name is minted.
- `dev.simplified.classbuilder.apt.ImplPlan` â€” the interface path's half of the same feature. `@ClassBuilder` on an interface emits `<Name>Impl` as plain source **text**, and that Impl is the only class a caller ever holds, so an annotation written on the interface has to reach it. **The round-trip route was rejected**: the Impl already declared `equals`/`hashCode`/`toString` unconditionally, so copying the annotation onto it and letting a later round mutate it produces duplicate members. The bodies are emitted directly instead, driven through the same `MemberShape` table the AST path reads - which is also what fixes the defect that was already there, since the Impl compared an array-typed accessor with `Objects.equals` and hashed it with `Objects.hash`. `identity`, `callSuper`, `useAccessors` and `cacheHashCode` cannot apply on that path (the Impl is `final`, extends `Object`, and reads every member through its own accessor) and each is reported as a `NOTE` rather than silently ignored.
- `dev.simplified.equality.editor` â€” `WholeObjectAugmentProvider` (a seventh `lang.psiAugmentProvider`) and `WholeObjectLineMarkerProvider`. **For three of the four members the provider looks like it is doing nothing, and very nearly is**: `equals`, `hashCode` and `toString` are inherited from `Object`, so their absence is never an error and every call site resolves either way. What it buys is silencing IntelliJ's own "does not override equals()/hashCode()" and "object used as a `HashMap` key" reports on a type whose pair only arrives at build time, plus a Ctrl-click that lands on the annotation rather than on `Object`. `canEqual` and `$hashCode` are the half that is not cosmetic: both are **new** names, so without them a subclass override or a hand-written parent's `other.canEqual(this)` is unresolved. **A record is skipped outright** - the platform already models its implicit members, and neither of the two names that are not inherited can reach one anyway. This is the plugin's one provider whose regression is *silent*, which is why it has its own test class rather than riding on the inspections'.
- `dev.simplified.equality.inspect` â€” `WholeObjectConstants` (the PSI analogue of `MemberSelector`/`MemberPolicy`), `EqualsAndHashCodeInspection`, `ToStringInspection`. Mostly error-mirroring, with three checks that are not. **`SetIdentityFix` recommending `INSTANCE_OF_CANEQUAL` on a JPA `@Entity` or a type holding a lazily-fetched association is what lets `EXACT_CLASS` be the default without stranding proxy users** - the honest tension is that a corpus-optimal default is not necessarily a consumer-optimal one, and the inspection is how the other two constants stay one keystroke away. `AddCanEqualFix` covers the one failure no emission can prevent: a subclass overriding `equals` without the hook, which may not exist at processing time or even in the same compilation. And the container-of-array check is mirrored here because it is the check most likely to catch a mistake while the field is being typed rather than at the next build.
  - **`EqualityConsistencyInspection` is the one here that mirrors no diagnostic at all** - it reads *hand-written* pairs, on classes carrying no annotation of this project's, and reports a split between what `equals` compares and what `hashCode` hashes. **The two directions are different findings and that split is the whole design**: a `hashCode` reading more than `equals` is a contract break (`WARNING`) since equal objects hash apart and one goes missing from every hash container, while a `hashCode` reading less is legal (`WEAK_WARNING`) because equal objects still agree on the smaller set. Folding the supertype is treated as a member, so `super.equals` without `super.hashCode` is the same finding as a dropped field. It exists because a split member set is **the one shape `@EqualsAndHashCode` cannot adopt** - one selection and one `callSuper` drive both members - so the check is the inventory of what must be decided before a hand-written pair can be replaced by the annotation. **No `LocalQuickFix`, deliberately**: closing a split means choosing which member set is the object's value, and the source does not record which. Four guards keep it off code that is fine - an opaque or delegating body yields no member set and is skipped outright rather than compared against a known one, a field assigned inside `hashCode` is a memo rather than a member, an accessor and the field behind it normalise to one member so the two sides may be spelled differently, and a target already carrying `@EqualsAndHashCode` is left to the inspection that owns it.
  - **`ReplaceableEqualityInspection` is its counterpart and the reason both are worth having**: one reports the hand-written pairs the annotation cannot adopt, the other the pairs it would generate, so a class carrying a hand-written pair gets an answer either way rather than silence. `WEAK_WARNING` on the `equals` name identifier (the consistency check anchors on `hashCode`, so the two never stack), with a `LocalQuickFix` that writes the annotation and deletes both methods. **The match is exact and that is the whole safety argument** - the fix deletes code, so every statement must be a recognised guard, the cast local, or the returned chain, and every term the comparison the annotation emits for that member's declared type; a guard reading state, an unrecognised term, or a `float` compared with `==` where the annotation emits `Float.compare` drops the class from the report rather than reporting it with a caveat. **`hashCode` is deliberately held to a weaker standard** - same members, nothing more - because a hash *value* is not contractual, only its consistency with `equals`, and demanding the accumulator shape would reject nearly every hand-written pair to protect a number nobody may depend on. **The array case is reported rather than rejected**: `Objects.equals` on an array is reference identity where the annotation compares content, so adopting it *changes* equality - which is usually the point - and it gets its own message plus a fix named `(compares arrays by content)`. Both inspections share `HandWrittenEquality`, the single reading of "what state does this body touch"; a second implementation would let the two disagree about one class, which is the failure they exist to prevent.

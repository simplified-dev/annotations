Flags misuse of @EqualsAndHashCode, and the identity failures no generated member can prevent:
  • A target that carries no instance state to compare: an enum, whose constants are already unique; an annotation type; or an interface with no @ClassBuilder to give it an implementation to reach.
  • An equals or hashCode the author already wrote. The annotation generates neither, which would leave the type with an equality relation half written down and half not.
  • A supertype declaring either member final, which no generated override can compile past.
  • An annotated supertype asking for a different identity. One hierarchy cannot hold two identity relations without the comparison becoming asymmetric.
  • callSuper = YES on a type whose superclass supplies no implementation to call, and a left-to-resolve callSuper whose superclass declares one half of the pair and not the other - a hierarchy that is already inconsistent, and the one shape the resolution refuses to guess at.
  • of and exclude both set, or either naming a member the selection never reaches - the check that catches a rename leaving the string behind.
  • cacheHashCode on a record, whose body cannot declare the instance field the memo needs; beside a member that can change after construction; or beside a callSuper whose contribution is not decidable here.
  • The include and exclude markers on one member, the include marker on a @Lazy field or on a static, parameterised or void method, and either marker on a type carrying no @EqualsAndHashCode to narrow.
  • A member whose declared type hides an array behind a type parameter - List<byte[]>, Optional<byte[]>, Map<K, int[]> - or one declared bare java.util.Collection.
  • identity = EXACT_CLASS on a type a framework subclasses at runtime, with a fix that writes INSTANCE_OF_CANEQUAL.
  • A subclass overriding equals without overriding canEqual under INSTANCE_OF_CANEQUAL, with a fix that writes the hook.
  • A hand-written canEqual of the wrong shape - one that does not return boolean, cannot be passed the instance the generated equals hands it, takes something other than Object, or is declared so that no subclass can override it.
  • @BuilderIgnore on a member the equality relation still reads, with a fix that writes @EqualsExclude beside it.

Most of these mirror a diagnostic the annotation processor already emits, so what the inspection adds is timing and position: the processor can only report against the type, while this underlines the offending attribute, marker or member as it is typed.

The last five are not mirrors, and they are why the inspection earns its keep. A member holding an array behind a type parameter is the one limitation of the feature a reader cannot infer from the annotation: the container delegates to its element's equals, and an array inherits Object's, so the elements compare by identity and no generator can see through the wrapper. It deliberately does not fire on a plain array field of any depth - byte[], int[][] and Vector3f[] are all compared correctly, and warning on them would train the reader to ignore the case that matters.

identity = EXACT_CLASS is the default because it is a valid equivalence relation everywhere, where the liberal relations can be silently wrong. Its one real cost is that a runtime-generated subclass - a persistence proxy standing in for state that has not been loaded - compares unequal to the instance it represents. The recommendation fires only where such a subclass is expected, and offers the cooperating relation rather than changing the default underneath every other type.

The subclass check is the one failure no emission can catch: the subclass may not exist when the annotated type is compiled, or even in the same compilation, so an override of equals that leaves the inherited hook in place reinstates exactly the asymmetry the hook exists to remove.

A hand-written canEqual is reused rather than replaced - writing one is how an author opts into the protocol, so the generated equals calls that declaration instead of emitting its own. The reuse is matched on the name and the argument count, which leaves the rest of the shape to the author: a hook returning the wrong type fails inside a member nobody wrote, and one nothing can override reads exactly like the cooperating relation while behaving like the bare one.

@BuilderIgnore and the exclude marker stay independent on purpose. A field the caller does not supply to the builder is still part of what the value is, so the pair is reported as a prompt with the marker one keystroke away, never applied on the author's behalf. It fires only for a member the relation actually reads - a transient or @Lazy field has already left the selection, and there is nothing to reconcile. The fix is withheld where of or exclude already names the member: the marker would then be a second, contradicting statement about it, and the selection reports a name it can no longer reach as an error.

Hard rejections report at ERROR, matching the processor, since the build cannot complete - as does a canEqual the generated equals cannot call at all. A stale memo, a container of arrays, a bare java.util.Collection and an unoverridable hook report at WARNING - each compiles and each is wrong at runtime. The identity recommendation, the @BuilderIgnore prompt and the informational checks report as weak warnings: they propose a change rather than report a defect.

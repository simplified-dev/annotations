Flags misuse of @Getter and @Setter:
  • @Setter on a final field - there is no assignment to generate.
  • @Setter beside @Lazy. The field's storage is a Lazy<T> wrapper, so the generated assignment does not type-check.
  • @Getter beside @Lazy, which already synthesises a memoizing accessor - redundant rather than wrong, so the second one is simply not emitted.
  • Either annotation on a record or an interface. Only classes and enums are supported: a record's components are accessors already, and an interface declares no state to read or write.
  • A name pattern with no {} placeholder, which gives every field the same method name, or one set to the "-" sentinel, which would be minted verbatim as the method name. Write AccessLevel.NONE to generate nothing.

Every check mirrors a diagnostic the annotation processor already emits. What this adds is timing and position: the processor can only report against the field, while the inspection underlines the offending annotation or attribute as it is typed.

The per-field checks carry the processor's asymmetry. A rejection that arises from a type-level annotation is silent, because fanning out over a class is a blanket request rather than a claim about any one field - a bare @Getter on a class with one final field is correct code. Only a field the author singled out with its own annotation is reported. The @Lazy clash with @Setter is the exception and is reported wherever the annotation was written, since it is the one case that reaches javac as a type error on a line nobody wrote.

Hard rejections report at ERROR, matching the processor. The redundant @Getter reports as a weak warning: the accessor the author asked for exists either way, so nothing is broken.

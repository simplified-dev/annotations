Flags misuse of @Log, the annotation that generates a log4j2 logger field into the type it is written on:
  • @Log on an interface, a record or an annotation type - none of them can hold the field the annotation exists to generate, so the annotation would have no output at all.
  • @Log(name = "-") - suppressing the field leaves the annotation with nothing to do, unlike a per-field name where one member among many can be turned off.
  • @Log(name = ...) that cannot expand to a legal Java identifier - the generated field would not compile, on a line that is not in the source.
  • log4j2 missing from the module's classpath - the generated field is injected rather than written, so it carries no source line for the compiler to report against; this names the dependency to add instead.
  • A type that already declares a field under the resolved name - the annotation backs off rather than emitting a duplicate, so it silently generates nothing. A field inherited from a supertype is not a collision and is not reported.

The generated field is private static final and named log unless name says otherwise. log4j2 must be on the annotated module's own classpath: the annotation library carries no dependency on it and refers to Logger by name only. Add org.apache.logging.log4j:log4j-api to compile, and a binding such as log4j-core to log at runtime.

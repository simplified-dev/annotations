Flags misuse of @ToString:
  • A target that carries no instance state to print: an enum, an annotation type, or an interface with no @ClassBuilder to give it an implementation to reach.
  • A toString the author already wrote. It is kept and the annotation generates nothing, so the annotation is a silent no-op.
  • A supertype declaring toString final, which no generated override can compile past.
  • callSuper = YES on a type whose superclass supplies no implementation to call.
  • of and exclude both set, or either naming a member the selection never reaches - the check that catches a rename leaving the string behind.
  • The include and exclude markers on one member, the include marker on a @Lazy field or on a static, parameterised or void method, and either marker on a type carrying no @ToString to narrow.
  • @BuilderIgnore on a member the dump still prints, with a fix that writes @ToStringExclude beside it.

Every check bar the last mirrors a diagnostic the annotation processor already emits. What this adds is timing and position: the processor can only report against the type, while the inspection underlines the offending attribute or marker as it is typed.

The already-declared check carries the deliberate asymmetry with @EqualsAndHashCode, which reports the same shape as an error. A written toString is a diagnostic rather than a contract, so an annotation that quietly generates nothing costs the reader an expectation and nothing else - which is what a prompt is for, rather than a failed build.

@BuilderIgnore and the exclude marker stay independent on purpose. A field the caller does not supply to the builder is still state a debugger dump wants to show, so the pair is reported as a prompt with the marker one keystroke away, never applied on the author's behalf. It fires only for a member the dump actually prints - a @Lazy or static field has already left the selection, and there is nothing to reconcile. The fix is withheld where of or exclude already names the member: the marker would then be a second, contradicting statement about it, and the selection reports a name it can no longer reach as an error.

Hard rejections report at ERROR, matching the processor, since the build cannot complete. The two prompts - a written toString, and a builder-excluded member still printed - report as weak warnings, because both compile and both may be exactly what was wanted.

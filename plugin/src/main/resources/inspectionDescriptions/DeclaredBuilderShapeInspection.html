Reports a builder declared beside @ClassBuilder whose shape cannot carry the generated members.

The processor refuses these with a compile error, and until this fires the editor had no analogue: the whole generated surface appeared in completion on a class the build was going to reject, so the first sign of the problem was a failure inside code the author never wrote.

The shapes refused, each for a reason the generated members cannot work around:

  • Not static - an inner class captures the enclosing instance, so the static entry point has nothing to create one from.
  • abstract where the entry points instantiate it - the builder a standalone target or a concrete link declares is what builder() calls new on.
  • The wrong type parameters - the generated members are written in the builder's own re-declared parameters, so they have to be present and in the same order for a setter to name a slot's type at all.
  • An unbounded trailing pair on a self-typed builder - a setter returning it would return something with no members.
  • The wrong extends clause - a chained builder inherits the parent's setters through it, so it has to name the annotated ancestor's builder, qualifier included, and pass it the ancestor's own arguments followed by the link and its builder, or on an abstract builder its own trailing pair.
  • A build method returning something else, on a chain only - the method a link inherits has to be the one its role declares, or on a root the root itself, which every link's build method overrides. Standing alone nothing generated calls build(), so an author's own is kept whatever it returns.

A target in a SuperBuilder chain merges into its declared builder as well, so a root, a concrete link and a chained abstract are each judged against the shape their role generates. A link whose annotated ancestor declares a builder the extends clause cannot name is reported on the annotation instead, whether or not the link declares its own.

A constructor or static factory target merges into the builder its enclosing type declares, so that builder is judged the same way. Its type parameters are measured against the ones the generated members are written in: a static factory's own, and the enclosing type's for a constructor.

On a shape the merge accepts, a field the author declares in the builder under a slot's name is also checked against the type the generated setters assign, type arguments included. That is the field's declared type, except for a @Lazy field and a field whose kept initializer reads the instance - names this, super or an instance member - which the builder holds as a Supplier of it: so private String note; beside a @Lazy String note is reported, and private Supplier<String> note; is not. A @Collector slot whose initializer reads the instance is held in a scratch container and is not checked here.

On a constructor or static factory target, a @BuilderSeed parameter is appended to the declared builder as a final field, and only the author's constructors can assign it. A constructor that leaves it unassigned is reported, as is a builder declaring no constructor at all - javac refuses both - unless an instance initializer of the builder assigns it, which assigns it for every constructor.

On a class or record target and on a constructor or static factory target, a builderConstructorAccess written on the annotation while the declared builder declares a constructor of its own is reported as a warning on that attribute: the author's constructor keeps the access it is written with. Where the declared builder declares no constructor, its implicit default takes the attribute's access instead.

Shape rejections are reported at error level because the alternative is javac failing on a generated line. The message is the one the processor prints, rendered from the same decision, so the editor is red exactly where and for exactly the reason the build is.
